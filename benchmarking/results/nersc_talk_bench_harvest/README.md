# NERSC `mycelia_talk_bench` harvest

Twenty result JSONs from five Perlmutter runs of the data-processing and k-mer
analysis benchmark suites, harvested 2026-08-05. None had ever been tracked in
this repo.

The harvest began as a reconciliation task: was
`rhizomorph_correction_validation_sweep_20260711_125013.csv` the output of job
`55134880`, or a distinct run?

## Answer

Unrelated. `55134880` is `mycelia_talk_bench`; the 2026-07-11 CSV is a separate,
later correction-validation sweep with a different schema
(`reference,genome_len,error_rate,regime,readlen,tech,…`). They share no
artifacts. The job's own stdout ends with a `--- result JSONs ---` inventory
whose newest four entries are this job's outputs; the CSV appears nowhere in it.

That inventory is `ls -t results/*.json | head`, so it lists only the **ten**
newest files. That truncation matters — see "A correction this note already
needed", below.

## Provenance

Verified byte-identical to the Perlmutter originals: per-file `md5` compared
pairwise against remote `md5sum`, all twenty matching. Confirmed absent from all
prior git history via `git log --all --diff-filter=A` (four first added in
`dd4d3263`, sixteen in `00e57612`, none earlier).

Filenames are upstream-generated by `01_data_processing_benchmark.jl` and
`02_kmer_analysis_benchmark.jl` and are kept exactly as produced, so the
byte-identity claim above stays checkable.

## Measurement conditions

AMD EPYC 7763 (64-core), Julia 1.10.10, 540 GB total memory. K-mer analysis
covered k ∈ {11, 15, 19, 21} across genome sizes {10000, 50000, 100000}, total
sequence length 800000. Data processing covered 5 files / 4.24 MB per run,
constant across all five.

## How to read these numbers

**Smoke-test-grade, not benchmark-grade.** Do not cite them as performance
results without re-measurement.

1. **Throughput varies ~7× across runs on identical input.** All five processed
   the same 5 files / 4.24 MB:

   | Run | `throughput_mbps` |
   | --- | --- |
   | 2026-06-19 12:09 | 25.20 |
   | 2026-06-19 12:44 | 4.80 |
   | 2026-06-20 07:51 | 14.74 |
   | 2026-06-22 10:52 | 33.82 |
   | 2026-06-27 09:02 | 32.58 |

2. **Timings are dominated by JIT warm-up.** `kmer_counting_k11_size50000`
   reports `min 11.4 ms`, `median 11.7 ms`, `mean 183 ms`, `max 527 ms`,
   `std 298 ms` — std ≈ 25× median, stable at 24.7–26.5× across all five runs.
   The same mean-and-std-far-above-median shape recurs throughout, though less
   extremely: k15/k19/k21 are 8.1–8.4×, `count_records_file1` 5.9×.
3. **MPI was not available.** `libmpi_gnu_123.so` failed to load
   (`libfabric.so.1: cannot open shared object file`). Single-node, non-MPI.
4. **The memory-fit estimator was emitting nonsense** — requests of 32.000 TiB
   and 32768.000 PiB against 478.241 GiB free, from
   `src/utility-functions.jl:740` (still the `@warn "Matrix may not fit in
   available memory!"` line in the current tree). Tracked separately.
5. **`k_mer_throughput_per_second` omits k=21** in all five comprehensive files,
   despite k=21 being in `k_values_tested`. That series is partial.

They are committed because they are hardware- and date-specific observations
that cannot be reconstructed from the repo — not because they are strong
measurements.

## Layout

Bundled rather than flat, matching the dominant convention in
`benchmarking/results/` (a run directory holding its artifacts plus its own
provenance). Before this harvest the flat top level held exactly one `.json`,
and it was undated; twenty flat dated JSONs would have become the largest group
there and set a competing precedent.

`git check-ignore` clears all twenty: `benchmarking/results/.gitignore` excludes
only `*_perkmer_*.jsonl` and `stage0_calibration_*.json`, and the root
`.gitignore` excludes only `track_a_baseline/refs/`, `track_a_baseline/cells/`
and `td-jt7r-*/`.

## A correction this note already needed

An earlier draft harvested only the 2026-06-27 run and listed the unharvested
remainder as "2026-06-22, 2026-06-20." Four runs were unharvested, not two: the
list was derived from the job stdout's `--- result JSONs ---` block, which
`head`-truncates to ten entries and therefore *could not* have shown the two
2026-06-19 runs. The accompanying sentence — that their absence was "a recorded
decision rather than a silent drop" — was false for exactly the runs it failed
to name.

A second review round then caught two further errors in the rewrite itself: it
described that inventory block as naming "four" files when it names ten, and it
carried the single-run figure 32.58 MB/s into a document now describing five
runs whose throughput spans 4.8–33.8 MB/s. Both are the same mistake as the
first — a number or claim true of one artifact, restated as true of the set.

Provenance notes are worth having only when checked against the directory and
against every run they claim to cover, not against another artifact's summary.
